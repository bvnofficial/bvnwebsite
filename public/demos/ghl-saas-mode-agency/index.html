Section 03

Transcript to summary, on the contact record, automatically

Your post asked me to advise on native versus third party. My honest answer is start native and only add a layer where native falls short. Native GoHighLevel handles the trigger, the recording and the write back. Where I add Make is transcription reliability and the strict prompt contract, because that is where native gives you the least control.

01
Call completed trigger inside the sub-account
A workflow on the Call Status trigger fires on completed inbound and outbound calls and posts contact id, call id, direction, duration and location id out to the scenario.
GHL workflow
02
Filter, 20 seconds or more
Voicemail drops, misdials and hang ups never reach the AI. This one filter is what keeps the contact timeline clean and the running cost near zero.
Make filter
03
Wait, then pull the recording and transcript
Short delay so the recording finishes writing, then the GoHighLevel API v2 conversations endpoint for the recording and the native transcript on that message id.
GHL API v2
04
Router, native transcript or fallback
If the native transcript exists, use it and skip the cost. If it does not, the audio goes down a Whisper branch with speaker separation instead of the whole thing failing.
Make router
05
Pull contact context first
Fetch the contact so the model sees pipeline stage, custom fields and earlier summaries. Context is the difference between a summary and a note somebody actually reads.
GoHighLevel
06
Structured prompt, JSON out
One model call against a locked prompt and a fixed schema covering purpose, outcome, commitments, objections, next steps and sentiment. JSON, never prose, so nothing downstream has to guess.
AI step
07
Summary written to the contact record
Posted as a note on the contact id that came from the call payload itself, so a shared number or a duplicate record can never misroute it.
GHL API v2
08
Fields, tags and pipeline movement
Outcome, sentiment and next action date land in custom fields, tags get applied, and the opportunity moves stage. This is what makes the follow up sequences fire on their own.
GoHighLevel
09
Dedupe store, retries and error alert
Every processed call id is stored and checked first, API modules retry three times, and a failure pings you with the call id and the reason. Silence is never treated as success.
Make error route

Section 05

The prompt contract

The model is not asked to write nicely. It is asked to fill a fixed schema and to leave a field empty when the call did not cover it. That one rule is what stops AI summaries from quietly inventing a commitment nobody made.

// AI step output, enforced schema
{
  "purpose":     "string",
  "outcome":     { "summary": "string", "result": "won | progressed | stalled | lost | unknown" },
  "commitments": [ { "who": "us | them", "what": "string", "due": "date | null" } ],
  "objections":  [ "string" ],
  "next_steps":  [ { "action": "string", "owner": "us | them", "due": "date | null" } ],
  "sentiment":   { "label": "warm | neutral | cool", "why": "string" },
  "stage_move":  "pipeline stage name | null",
  "tags":        [ "string" ]
}

// Rules baked into the system prompt
// 1. Never state a number, date or commitment that was not said on the call.
// 2. Empty beats a guess. Unknown is a valid answer.
// 3. Quote them when the wording carries the meaning.
// 4. Next steps are actions with an owner, not observations.
// 5. Only propose a stage move that exists in this sub-account's pipeline.
Section 06

The parts that decide whether you still trust it in month three

Anyone can wire the happy path. Clean and reliable is what happens on the other days.

Snapshot updates do not wipe data

Version the master, push updates deliberately, and test on a sandbox sub-account first. Existing contacts, pipelines and history stay intact.

No duplicate summaries

Every processed call id goes to a data store and is checked first. A replayed webhook or a manual rerun cannot post the same summary twice.

Recording lag handled

The recording can lag the call end. The scenario waits, retries three times, then takes the fallback transcription branch instead of dying quietly.

Cost stays small

The short call filter runs before any AI step, native transcript is used when it exists, and long calls are chunked so nothing hits a token wall.

Wrong contact is impossible

The contact id comes from the call payload, never from a phone number lookup, so shared numbers and duplicate records cannot misroute a summary.

You own all of it

Your agency account, your Make account, your keys. Named workflows, documented snapshot, a written runbook. No lock in to me.
